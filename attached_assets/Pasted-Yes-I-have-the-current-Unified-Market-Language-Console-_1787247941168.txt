2. The most important problem: the memory can leak into evaluation

This is the biggest issue I see.

You have:

starting_buckets = load_experience() if args.resume else None

and then:

result = run_walk_forward(
    candles,
    args.horizon,
    args.start,
    args.limit,
    persist=args.persist,
    initial_buckets=starting_buckets,
)

If you run:

walk-forward --persist

and later:

walk-forward --resume

the second evaluation starts with knowledge learned from the previous run.

That is fine for operational learning.

It is not fine for measuring out-of-sample predictive performance unless the evaluation period is strictly later than everything contained in the memory.

Human meaning

Imagine:

Candle #500 → prediction → future revealed → memory learns.

Then you restart the program and load that memory.

Now the model already knows historical outcomes from candle #500 onward.

If you evaluate those same candles again, you are no longer testing a clean prediction.

So we need two explicitly separated modes:

Research mode

TRAIN → predict unseen OOS → reveal → score

Live-learning mode

existing memory → predict new candle → reveal later → update memory

Those must never be mixed.

4. The retrieval algorithm is too simple

Currently:

score = sum(
    1.0 for a, b in zip(current, parts)
    if a == b
) / len(current)

So every feature gets exactly the same importance.

For example:

direction        = 1 point
trend            = 1 point
structure event  = 1 point
sequence         = 1 point
momentum         = 1 point
regime           = 1 point

But these features do not necessarily carry equal predictive information.

More importantly, the retrieval system does not yet answer:

Are the retrieved states actually more similar than randomly selected historical states?

That's the retrieval-discrimination test we discussed earlier.

We need to measure that explicitly.

7. There is a hidden issue in candle normalization

This part:

recent = candles[max(0, index - 20): index + 1]

includes the current candle.

Then:

average_range = sum(...) / len(recent)
average_body = sum(...) / len(recent)

includes the candle being classified.

This is not necessarily future leakage—the current candle is known at prediction time—but it makes the classification self-referential.

For example:

Current candle becomes unusually large.

It simultaneously increases the average used to decide whether it is unusually large.

A cleaner causal formulation is:

previous candles → baseline
current candle → compared against baseline

So:

baseline = candles[index-20:index]
current = candles[index]

That gives a much cleaner definition:

"How unusual is this candle compared with what existed immediately before it?"

8. change is calculated but unused

That is harmless, but it indicates the state representation is still evolving.

We should either:

For a research system, I prefer the latter only when the feature has a defined purpose.

11. The current confidence system is not predictive confidence

You currently have:

That means:

"We are confident in the prediction."

Those are not the same thing.

You can have:

So confidence should eventually incorporate:

12. The outcome threshold needs to be treated as a research parameter

Currently:

threshold = max(start * 0.001, 1e-9)

So the classification is essentially:

> +0.10% = bullish
< -0.10% = bearish
otherwise = neutral

That's a reasonable starting experiment.

But it is not universally correct.

For gold 5-minute candles, the meaningful movement threshold should eventually be evaluated relative to:

ATR
volatility regime
timeframe
spread/noise
horizon

Otherwise the outcome label itself may dominate the apparent predictive performance.

13. Another important issue: persist does nothing inside run_walk_forward

You pass:

into:

but inside the function the persist argument isn't actually used.

Persistence happens later:

if args.persist:
    save_experience(result["buckets"])

So this isn't a functional error, but the API is misleading.

We should clean that up.

14. The good part: prediction chronology itself is correct

This part is important.

You have:

forecast = predict(state, buckets)
actual = outcome_at(candles, index, horizon)

followed by:

buckets.setdefault(state.key(), ExperienceBucket()).observe(actual)

That ordering is correct.

Human language:

The system makes its prediction before looking at the future.

Then:

The future is revealed.

Then:

The experience memory learns from the result.

That is exactly the causal principle we want.

So I would preserve this architecture.
